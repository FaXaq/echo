# Infrastructure ports close over adapters, not per-call context

Every `packages/modules/src/<module>/infrastructure` function an `app/` function depends on — same module or cross-module — is a **port**: a `.<command|query|check>.port.ts` type plus a `PortFactory`, implemented by a `.<command|query|check>.<adapter>.ts` (e.g. `.kysely.ts`, `.better-auth.ts`). `app/` functions receive the port instance through `deps`; they never import and call an `infrastructure` function directly, in their own module or another's. This is what lets app-layer tests inject a literal fake function typed against the port instead of `vi.spyOn`-ing the real module — the concrete failure mode observed before this ADR (`file/app/rename-file.test.ts` had to spy on `infrastructure/index.ts` because `rename-file.ts` called `renameFileById` inline).

Two kinds of dependency exist and each is threaded differently. Stable external adapters (an auth client, mailer, S3, geocoding) are closed over by the factory: `PortFactory = (deps: { auth, headers, ... }) => Port`. Per-call context that cannot be a singleton — `db`, and especially `OrganizationScope` (ADR-0002, ADR-0003: a per-request authorization proof, structurally impossible to bake into a factory closure) — stays an explicit argument on the port itself: `Port = (db, scope, input) => Result`. These aren't two competing conventions to pick between; they're the same rule applied to two different dependency shapes. A port with no adapter dependency gets a zero-arg factory (`() => Port`) rather than a forced empty `deps: {}`.

Filenames carry the CRUD role: `.command.` for writes, `.query.` for reads, `.check.` for capability/permission checks that are neither. Infrastructure helpers used only by other infrastructure (e.g. a `common.ts` used inside several `.kysely.ts` files) don't get their own port — the boundary that matters is `app/` → `infrastructure/`, not `infrastructure/` → `infrastructure/`.

We chose this over leaving each module free to shape its own DI (the state before this ADR: `calendar` had db/scope-as-args with no closure, `organization` had closure-only with no db/scope, `file`/`user`/`plan`/`place`/`invitation`/`notification` had no ports at all) because the divergence was silently degrading test quality module by module, and a newcomer reading `organization`'s factory shape next to `calendar`'s would have no way to tell which was the pattern to follow.
